## Step 2.1 approval and read-only compatibility policy

- The user reported Step 1.1 “working well” and approved proceeding to Step 2.1. The specific unverified Phase 1 cases are named in the Step 1.1 evidence; proceeding is not a claim they all passed and does not waive later Enterprise acceptance.
- The approved read-only boundary requires a refinement to the originally planned status command. Official [v2.81.0 status source](https://github.com/cli/cli/blob/v2.81.0/pkg/cmd/auth/status/status.go) and [release](https://github.com/cli/cli/releases/tag/v2.81.0) establish JSON status availability (commit `52ba8366057b94a77d2e4b2fc99de56e100e45bf`). Official [v2.102.0 status source](https://github.com/cli/cli/blob/v2.102.0/pkg/cmd/auth/status/status.go) predates automatic refresh. Official [v2.103.0 status source](https://github.com/cli/cli/blob/v2.103.0/pkg/cmd/auth/status/status.go) and [release](https://github.com/cli/cli/releases/tag/v2.103.0) add automatic credential refresh and `--no-refresh` together (commit `7948e8056e45ac3c729b829e0eafe2d0797a95c6`); [v2.105.0 source](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/auth/status/status.go) retains the flag (commit `e1219499a578b69e3437adaa31cd60614e23c802`).
- For official stable 2.81–2.102, the intended status arguments use the legacy JSON form. Starting with 2.103, `--no-refresh` is mandatory; unsupported capability must fail closed without retrying the mutating default. Versions before 2.81 are unsupported for structured status, while binary readiness remains separate. Unknown major/future versions must not be assumed to have legacy behavior. These source-version observations do not establish behavior for arbitrary modified forks or live Enterprise acceptance.

## Step 3.1 integration boundary

- The user approved proceeding to Step 3.1, without representing individual pending Phase 2 manual checks as passed. The implementation adds a typed, bounded owned-process streaming API alongside the existing public command runner; authentication output is interpreted into fixed safe categories rather than logged as raw tails.
- Login currently accepts only stable CLI versions 2.101.0 through 2.105.0, not arbitrary future versions or modified forks. Read-only status version policy above is unchanged. The pinned v2.101.0 [login command](https://github.com/cli/cli/blob/v2.101.0/pkg/cmd/auth/login/login.go), [auth flow](https://github.com/cli/cli/blob/v2.101.0/internal/authflow/flow.go), [shared login flow](https://github.com/cli/cli/blob/v2.101.0/pkg/cmd/auth/shared/login_flow.go), and [Git credential setup](https://github.com/cli/cli/blob/v2.101.0/pkg/cmd/auth/shared/git_credential.go) inform the noninteractive policy: prompting is disabled, credential prompting and Git-helper setup are skipped, and HTTPS changes the CLI host protocol configuration. CLI-owned credential/config persistence is consented, not a claim of zero writes. The OAuth flow may fall back to local web flow; unexpected output must fail safely, not be guessed.
- The stable login allowlist is specifically 2.101.0, 2.102.0, 2.103.0, 2.104.0 and 2.105.0; other patches are not included. In addition to the v2.101.0 sources above, pinned [v2.103.0 login](https://github.com/cli/cli/blob/v2.103.0/pkg/cmd/auth/login/login.go) and [v2.105.0 login](https://github.com/cli/cli/blob/v2.105.0/pkg/cmd/auth/login/login.go) sources bound the reviewed range. This is a source/fixture restriction, not a blanket live compatibility claim.
- Final automated integration evidence is in [Step 3.1](step-3.1.md): 156 tests passed, including focused model gates and owned-process cleanup. Manual GitHub.com verification remains pending and Enterprise access testing remains blocked; neither is waived.

- User-approved clipboard policy: GitHub CLI attempts automatic copy; the app's Copy code button remains the manual fallback instead of implementing a second automatic copy path.
